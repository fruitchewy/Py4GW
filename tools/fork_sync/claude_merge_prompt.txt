You are performing an automated fork sync for the Py4GW repository.

## Context

Py4GW is a Python-based library for the game Guild Wars. Multiple contributors
maintain forks with features that haven't been upstreamed. This repo aggregates
those fork-exclusive features alongside the upstream codebase.

## Your Task

The sync script has already pulled exclusive directories from the fork using
plain `git checkout`. Those paths are owned entirely by the fork and need no
merge logic.

Your job is to reconcile the CORE TOUCHPOINT files — shared files that both
upstream and the fork may have modified. These files are passed to you as
arguments.

## Conflict Resolution Policy

The calling script passes a CONFLICT POLICY in the prompt. Read it carefully.

There are two modes:

### prefer_upstream (external forks)
Upstream is the AUTHORITY for shared code. The most common pattern is that
upstream fixes a bug in a shared library file, and the fork hasn't incorporated
that fix yet. On conflicts, keep upstream. Only integrate clearly additive
content from the fork (new enums, new handlers, new imports).

### prefer_source (user's own branches)
The source branch is the AUTHORITY. The user intentionally made these corelib
changes. On conflicts, keep the source branch version. Upstream main is the
base being patched, not the authority.

## Instructions

For each touchpoint file:

1. Read the current (upstream-based) version of the file in the working tree.
2. Run `git show <fork_remote>/<fork_branch>:<file>` to see the source's full version.
3. Run `git diff <fork_remote>/<fork_branch> -- <file>` to see a line-level diff.
4. Classify each difference as one of:
   a. ALREADY PRESENT — source's content exists in our version. Skip.
   b. SOURCE ADDITION — new content in the source that doesn't exist in our
      version (e.g. a new enum value, a new handler, new logic). Integrate it.
   c. ONE-SIDED FIX — one side changed a line the other still has the old
      version of. Apply the conflict policy to decide which to keep.
   d. TRUE CONFLICT — both sides changed the same code differently.
      Apply the conflict policy. FLAG it for human review regardless.
5. When integrating additions:
   - For enum files: add the new enum values in the appropriate location.
   - For handler/dispatch files: add the new case handlers.
   - For any file: preserve the winning side's content and formatting.
6. Do not remove content from the winning side.

## Output

After processing all touchpoint files, print a summary:
- Which files were modified and what was added/changed.
- Which files needed no changes (fork content already present).
- Any conflicts found and how they were resolved (per the conflict policy).

Then stage the modified files with `git add`.

## Important

- Do NOT commit. The calling script handles commits.
- Do NOT modify any files outside the touchpoint list.
- If you are unsure about a change, skip it and flag it for human review.
